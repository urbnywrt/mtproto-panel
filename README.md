# MTProto Panel

Веб-панель управления MTProto прокси серверами. Позволяет централизованно управлять несколькими сервис-нодами, создавать и настраивать прокси, просматривать статистику и следить за подключениями.

> Это форк [danielVNru/mtproto-panel](https://github.com/danielVNru/mtproto-panel) с поддержкой **Telegram WEB proxy**.
> Установщик, `update.sh` и готовые образы (`ghcr.io/urbnywrt/mtproto-panel-*`) по умолчанию берутся из этого форка.
> Работает в паре с нодами [urbnywrt/mtproto-node](https://github.com/urbnywrt/mtproto-node).

## Возможности

- Управление несколькими сервис-нодами с единой панели
- Создание / редактирование / удаление MTProto прокси
- **VPN-туннелирование** — указание VLESS-подписки для прокси (трафик через зарубежный сервер)
- **Мультипортовые прокси** — назначение индивидуального порта каждому прокси
- Просмотр статистики: CPU, RAM, трафик, аптайм
- Подключённые IP-адреса с флагами стран
- Лимиты подключений на прокси (ограничение устройств)
- Чёрный список IP-адресов на уровне ноды
- Пользовательские домены для fake TLS (пул 50 доменов по умолчанию)
- Копирование ссылки `tg://proxy?...` или `https://t.me/webproxy?...` в один клик
- Приостановка / возобновление прокси
- Пересоздание контейнера прокси — так обновление ноды доходит до уже созданных прокси
- **WEB-прокси Telegram** — свой домен, статус и срок сертификата, перевыпуск в один клик
- Редактирование IP и домена ноды после её добавления
- Обновление сервис-ноды и самой панели из интерфейса с показом вывода скрипта
- Версия telemt на ноде и в каждом прокси; контейнеры на старой версии помечаются
- JWT авторизация
- Полностью на русском языке

## Совместимость

Скрипт установки протестирован и поддерживается на следующих системах:

| ОС | Версия | Пакетный менеджер |
|----|--------|-------------------|
| Ubuntu | 20.04, 22.04, 24.04 | apt |
| Debian | 11, 12 | apt |
| CentOS / RHEL | 8, 9 | yum / dnf |
| AlmaLinux / Rocky Linux | 8, 9 | yum |

> ⚠️ Скрипт предназначен только для Linux x86\_64 и aarch64. Windows и macOS не поддерживаются.

Скрипт автоматически установит недостающие зависимости: `curl`, `openssl`, `git`, Docker, Docker Compose.

## Быстрая установка

Одна команда для загрузки и запуска:

```bash
wget -qO /tmp/panel-install.sh https://raw.githubusercontent.com/urbnywrt/mtproto-panel/master/install.sh && sudo bash /tmp/panel-install.sh
```

Скрипт автоматически:
1. Установит Docker и Docker Compose (если отсутствуют)
2. Склонирует ветку `master` форка `urbnywrt/mtproto-panel` — `origin` будет смотреть на него же
3. Запросит настройки:
   - **Порт панели** (по умолчанию `80`)
   - **SSL**: без SSL, самоподписанный сертификат или Let's Encrypt
   - **Логин и пароль администратора**
4. Сгенерирует JWT-секрет и пароль БД
5. Скачает готовые образы из `ghcr.io/urbnywrt` (соберёт локально, если реестр недоступен) и запустит контейнеры

Панель установится в `/opt/mtproto-panel`.

### SSL

| Вариант | Что происходит |
|---|---|
| 1. Без SSL | панель по HTTP на выбранном порту |
| 2. Самоподписанный | сертификат на IP сервера, панель по HTTPS на выбранном порту |
| 3. Let's Encrypt | нужен домен с A-записью на сервер; на время выпуска certbot занимает порт 80 и останавливает nginx/apache/caddy на хосте. Продление — cron раз в два месяца |

Для вариантов 2 и 3 установщик создаёт `docker-compose.override.yml` и `nginx-ssl.conf`:
выбранный порт публикуется на HTTPS, а `PORT` в `.env` переписывается на `18080`
(там HTTP-редирект), чтобы не занимать хостовый 80.

## Обновление

Кнопка «Обновить панель» в настройках или по SSH:

```bash
cd /opt/mtproto-panel
sudo bash update.sh
```

Скрипт берёт код из `master` форка, тянет образы из GHCR (собирает локально, если их нет)
и перезапускает контейнеры.

Из интерфейса скрипт уходит работать в контейнер-спутник `mtproto-panel-updater`:
запущенный внутри бэкенда, он удалил бы контейнер вместе с собой на `docker compose down`.
Страница настроек ждёт завершения спутника и показывает вывод; журнал — `update.log`
в каталоге панели. Первое обновление панели, поставленной до этого исправления, — только
по SSH: кнопка запускает старую копию скрипта.

Каждая ветка публикуется в GHCR под своим тегом (`feature/foo` → `:feature-foo`),
`:latest` двигают только master и dev. При `bash update.sh --b=<ветка>` скрипт сам берёт
тег ветки. Флаги: `--build` — всегда собирать локально, `--pull` — взять `IMAGE_TAG`
(по умолчанию `:latest`) даже для ветки.

Если после обновления интерфейс открывается, а все запросы к API отдают 502 — значит
контейнер фронтенда работает на старом конфиге, где имя `backend` в `proxy_pass` задано
литералом: nginx резолвит его один раз при старте, а обновление меняет IP контейнера
бэкенда. Лечится обновлением образа фронтенда (`docker compose pull frontend &&
docker compose up -d`), в текущем конфиге имя резолвится на каждый запрос.

Перед обновлением `git status --short` должен быть пустым: локальные правки
отслеживаемых файлов (`docker-compose.yml`, `frontend/nginx.conf`) конфликтуют
с новой версией. Порт и образы задаются в `.env`, остальное — в
`docker-compose.override.yml`. При конфликте скрипт выходит до остановки панели
и печатает, что именно конфликтует, так что панель продолжает работать.

Панель, поставленная из репозитория автора, переводится на форк так же, как нода, —
см. [UPGRADE.md ноды](https://github.com/urbnywrt/mtproto-node/blob/master/UPGRADE.md):

```bash
cd /opt/mtproto-panel
git remote set-url origin https://github.com/urbnywrt/mtproto-panel.git
sudo bash update.sh
```

## Конфигурация (.env)

| Переменная | Описание |
|------------|----------|
| `PORT` | Хостовый порт HTTP панели (по умолчанию `80`). С SSL — `18080`, порт HTTPS задан в `docker-compose.override.yml` |
| `ADMIN_USERNAME` | Логин администратора |
| `ADMIN_PASSWORD` | Пароль администратора |
| `JWT_SECRET` | Секрет для JWT токенов |
| `DB_NAME` | Имя базы данных |
| `DB_USER` | Пользователь БД |
| `DB_PASSWORD` | Пароль БД |
| `IMAGE_REPO` | Реестр образов (по умолчанию `ghcr.io/urbnywrt`) |
| `IMAGE_TAG` | Тег образов (по умолчанию `latest`), можно закрепить на sha коммита |

## Использование

1. Откройте панель по адресу, который напечатал установщик (`http://SERVER_IP:PORT` или `https://...`)
2. Войдите с логином и паролем администратора
3. Добавьте сервис-ноду (IP, порт, токен)
4. Создавайте прокси, управляйте лимитами и чёрными списками

### Типы прокси

**Fake TLS** — обычный MTProxy, маскируется под TLS к чужому домену из пула.
Ничего, кроме ноды, не нужно.

**WEB** — прокси Telegram поверх обычного HTTPS-сайта: клиент ходит на ваш домен, а
не отличимый от статического сайта трафик несёт полезную нагрузку. Требуется своя
нода с поддержкой WEB (панель проверяет это сама и прячет тип, если нода старая),
домен с A-записью на ноду **без оранжевого облака Cloudflare** и токен Cloudflare со
`Zone:DNS:Edit` для DNS-01. Открывается в Telegram Desktop 7.1.0 и новее.

### Когда пересоздавать контейнер

Обновление ноды не меняет уже работающие прокси: их контейнеры продолжают жить на
прежних конфигах. Кнопка «Пересоздать контейнер» на странице прокси или в меню его
карточки собирает контейнер заново из сохранённых настроек. Секрет, домен и ссылка
сохраняются, прокси недоступен около 20 секунд.

## Развёртывание в России с VPN

Для работы MTProto прокси в РФ трафик до Telegram нужно пропускать через зарубежный VPN-сервер.

### Схема

```
Пользователь (РФ)
       │
       ▼
┌─────────────┐     ┌───────────────────┐     ┌──────────────┐     ┌─────────────┐
│  Панель     │────→│ Сервис-нода (РФ)  │────→│ VPN-сервер   │────→│ Telegram DC │
│  (любой IP) │     │ telemt + xray     │     │ (за рубежом) │     │             │
└─────────────┘     └───────────────────┘     └──────────────┘     └─────────────┘
```

### Инструкция

1. Установите панель на любом сервере (может быть в РФ)
2. Установите сервис-ноду на российский сервер
3. Подготовьте VPN-сервер за рубежом с xray/VLESS (Reality рекомендуется)
4. В панели при создании прокси укажите URL подписки VLESS
5. Сервис-нода автоматически создаст xray-туннель и проксирует трафик

### Поддерживаемые VPN-протоколы

| Протокол | Транспорт | Рекомендация |
|----------|-----------|--------------|
| VLESS + Reality | TCP | Лучший выбор — не детектируется DPI |
| VLESS + TLS | TCP / WS / gRPC | Хорошо работает |
| VLESS | TCP | Базовый вариант |
