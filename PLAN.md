# WEB proxy support — план реализации (mtproto-panel)

Ветка: `feature/web-proxy`. Ведущий план и вся архитектура — в `mtproto-node/PLAN.md`
(этапы 1–5 и 8). Здесь только этапы 6 и 7.

---

## 1. Поправка к ТЗ: миграции БД не требуется

`backend/src/db/migrations.ts` создаёт только таблицы `users` и `nodes`.
**Таблицы прокси в Postgres нет** — прокси целиком живут в JSON-сторе ноды.

`backend/src/routes/proxies.ts` — чистый pass-through: `proxyToNode()` перекидывает
`req.body` на ноду через `JSON.stringify` без какой-либо обработки.

Следствия:

- Пункт «миграция БД: новые поля nullable, откат безопасный» применять не к чему.
  Схему не трогаем — это максимально безопасный откат из возможных.
- Новые поля доедут до ноды сами, без правок бэкенда.
- Единственная содержательная работа на бэкенде — валидация, которой сейчас нет вообще.

Если понадобится кэшировать/агрегировать web-поля в панели (сводка сертификатов по всем
нодам) — отдельное решение, в этот план не входит.

## 2. Этап 6 — бэкенд: capabilities и валидация

### Проброс capabilities ноды
Нода на этапе 1 отдаёт `GET /api/capabilities` → `{ web, mode, bindIp, reason }`.
Добавить в `backend/src/routes/nodes.ts` проксирующий эндпоинт
`GET /:nodeId/capabilities`, чтобы фронт мог гейтить форму и не предлагать WEB там,
где 443 занят и `WEB_BIND_IP` не задан.

### Валидация
В `POST /:nodeId/proxies` и `PUT /:nodeId/proxies/:proxyId`, до `proxyToNode`:

- `type` ∈ `{'faketls','web'}`, отсутствует → `'faketls'`.
- При `type === 'web'` обязательны и проверяются:
  - `domain` — валидный FQDN, lowercase, без порта, схемы и завершающей точки.
    Для WEB задаётся всегда, из пула не берётся.
  - `acmeEmail` — валидный email.
  - `webCarrier` ∈ `{'https','https-lanes'}`, дефолт `'https-lanes'`.
  - `webSecretMode` ∈ `{'plain','dd'}`, дефолт `'plain'`.
  - `acmeDnsToken` — опционален (override для `CF_API_TOKEN` ноды). Если передан —
    в ответах наружу **не возвращать**.
- При `type === 'faketls'` web-поля отбрасываются, чтобы не протечь в конфиг ноды.
- В `POST` дополнительно прокидываем `nodeIp: node.ip` — нода сверяет с ним A-запись.
- Ошибки — `400` в существующем формате `{ error: string }`.

Отдельный коммит, отдельно от фронта. **Готово когда:** сборка проходит; создание
faketls-прокси работает ровно как раньше; создание web-прокси без `domain`/`acmeEmail`
даёт 400 и до ноды не доходит.

## 3. Этап 7 — фронтенд

### `frontend/src/api/index.ts`
Расширить типы прокси и `ProxyCreateRequest`/`ProxyUpdateRequest` новыми полями
(все опциональные) + `getNodeCapabilities(nodeId)`.

### `components/AddProxyDialog.tsx`
- В таб `basic` — селектор типа (`RadioButton`, уже импортирован): «Fake TLS» / «WEB».
- Тип по умолчанию `faketls`, существующий сценарий не меняется.
- Опция «WEB» **дизейблится**, если `capabilities.web === false`, с пояснением из `reason`
  («443 занят, задайте WEB_BIND_IP на ноде»).
- Зависимые поля появляются только при `web`:
  - домен (обязателен, свой домен оператора),
  - email для ACME,
  - carrier (`Select`: `https-lanes` / `https`),
  - режим секрета (`Select`: `plain` / `dd`),
  - Cloudflare API token (опционально, если на ноде нет `CF_API_TOKEN`).
- **Заметная подсказка про DNS-only**: A-запись обязана быть с серым облаком и указывать
  на `capabilities.bindIp`. Оранжевое облако ломает WEB полностью — это самая вероятная
  ошибка оператора, и preflight ноды её отбивает, но лучше предупредить заранее.
- При `web` скрываем неприменимое: выбор домена из пула, `listenPort` (клиент требует
  ровно 443), `maskHost`.
- Блок VLESS/туннеля доступен для обоих типов — на ноде `[[upstreams]]` общая секция.

### `components/EditProxyDialog.tsx`
- Тип показываем, **менять запрещаем**: смена типа означает другой домен, конфиг и сертификат.
  Требуется пересоздание прокси.
- Для `web` даём править email, carrier, режим секрета; домен — только с предупреждением,
  что потребуется новый сертификат.

### `components/ProxyCard.tsx`
- Бейдж типа (`Label`) рядом с существующим бейджем статуса.
- Для `web` — бейдж статуса сертификата: `pending` / `active` (с датой истечения) /
  `error` (с `certLastError` в тултипе).
- Кнопка копирования отдаёт ссылку нужного формата. Формат приходит с ноды
  (`GET /:id/link`), панель его сама не собирает.

### `pages/ProxyDetail/ProxyDetail.tsx`
- Тип, домен, carrier, режим секрета, статус и срок сертификата, ссылка нужного формата.

**Готово когда:** `yarn build` проходит; карточка faketls-прокси визуально не изменилась
кроме нового бейджа типа; web-прокси создаётся из формы и его ссылка копируется в виде
`https://t.me/webproxy?server=...&secret=...`.

## 4. Обратимость

Изменений схемы нет. Откат — `git revert` ветки. Старые записи прокси без `type`
трактуются как `faketls` и на фронте, и на ноде.

## 5. Что добавилось сверх плана

Всплыло при раскатке на прод и осталось в ветке:

- **Редактирование ноды** (`EditNodeDialog`) — IP и домен раньше правились только руками
  в базе, а домен, не заданный при создании, задать было негде.
- **Пересоздание контейнера прокси** — единственный эндпоинт ноды, до которого панель
  не дотягивалась. Без него обновление ноды не доходило до уже созданных прокси, и
  чинить приходилось curl'ом по SSH.
- **Вывод результата обновления ноды** — кнопка «Обновить» сообщала об исходе только в
  консоль браузера: успех и падение выглядели одинаково.
- **Валидация и сокрытие секретов на бэкенде** (`validation.ts`) — `acmeDnsToken`
  не возвращается клиенту, входные данные проверяются до отправки на ноду.
- **Ошибки действий видны пользователю** — пауза, перевыпуск сертификата и пересоздание
  контейнера пишут причину в алерт страницы, а не в консоль.
